# Erlang/OTP Modules and Code Loading

## Reference

Erlang/OTP, “Modules,” *Erlang/OTP Reference Manual*, and “Compilation and
Code Loading,” *Erlang/OTP System Documentation*, current online edition
accessed 2026-08-21.
[Modules reference](https://www.erlang.org/doc/reference_manual/modules.html);
[code loading](https://www.erlang.org/doc/system/code_loading.html).

The pages are living documentation; they identified themselves as OTP
29.0.5 when consulted.

## Research question or contribution

How does the BEAM's source language bind module identity to file names,
structure a compilation unit, and mark files as tool-generated?

## Method

The module-syntax and code-loading chapters were read for the module
declaration's placement and filename rule, per-file module structure, and
generated-source conventions. Compiler behavior and tutorials were not used
as authority.

## Findings

- Erlang code is divided into modules; a module is a sequence of attributes
  and function declarations in one file.
- The `-module(Module).` attribute declares the module's name. It is the
  only mandatory attribute, and it is to be specified first.
- The declared name is to be the same as the file name minus the `.erl`
  extension; the documentation states that otherwise code loading does not
  work as intended. The name is an atom, and the declaration, not the
  filesystem, carries it.
- Object files are named after the module with the `.beam` suffix, and the
  code server locates them by module name on the code path — the filename
  rule is what makes name-based loading possible.
- The `-file(File, Line).` attribute exists so tools such as Yecc can inform
  the compiler that source is generated by another tool and map generated
  positions back to an original user-written file.
- Code replacement is module-level, with current and old module instances
  coexisting — reinforcing the module, not the file, as the unit of
  identity.

## Relevance

This is the closest target precedent for Catena's chosen model: a mandatory
first module declaration whose name must equal the file basename, one
module per file, artifacts named after the module, and a distinct
generated-source mechanism with provenance. Catena adopts the
declared-name-plus-must-match rule and the generated-marker need, while
specifying the mismatch as static invalidity with a stable diagnostic
rather than an informal expectation, and reserving all loading and
replacement behavior to later runtime slices.

## Limits

Erlang's rule is stated as guidance for code loading rather than a
compile-time rejection; its atoms admit far more than ASCII names; and its
attribute-oriented header is a concrete declaration syntax that belongs to
P109, not to the abstract file-unit boundary. The generated-file `-file`
attribute maps positions rather than marking whole files.
