# C040 Built-In Data Model

## Observations

Checklist item G040 is complete as C040 and normative source-only
language revision `0.1.35`, opening Section 5 with its anchor. The
completed boundary fixes: the twelve-way classification — the seven
shipped types (unit, Bool, Int, Float, tuple, function, process
handle) restated unchanged; Text, Character, and Bytes as built-ins
elaborated from C017's scanned literals by the C018 pattern;
list, map, and set as library territory (G101 declares them as
ordinary nominal ADTs); and references excluded (G084) — with the
three new types comparable and orderable by content (lexicographic
scalar order for Text and Character, byte order for Bytes) and
living at the meaning and classifier level until a frontend encodes
their literals. Zero new diagnostic families.

Four implementation decisions worth recording. First, the
**character payload is the code point, not a binary**: runtime
verification showed `Catena.scan_literal("'é'")` delivers payload
`233` — C017 decodes the character kind to its scalar directly. The
first draft of `Catena.Text` treated it as a binary and failed on
`String.to_charlist(233)`; the corrected module pattern-matches
`is_integer(payload)` for the character kind, and `Text.Meaning`'s
value type is `binary() | non_neg_integer()`. Second, the
**classifier binary-ambiguity resolved conservatively**: `Catena.Values`
now admits any binary as a value (a bare Elixir binary is Text or
Bytes content — the classification observes content per C037), with
the elaborated `Text.Meaning` struct also classifying as a value;
this intentionally flipped C029's pin (`refute Values.value?("string")`
became an assertion — the classifier is a living consumer and the
classification extended it, the journal's record of the change).
Third, the **content orders ride Elixir's byte-wise binary
comparison**: for valid UTF-8, byte order coincides with scalar
order, so one primitive gives both the Text and Bytes orders
truthfully; Character compares its integer code points directly.
Fourth, the **lifecycle feature collision recurred** (the third
time — C033, C036, now C040): the `built-in-data-model` feature
entry was lost to a multi-edit collision and caught by the
registration test's `{:ok, :stable}` assertion — the per-area state
assertion keeps earning its place.

merged into the `rewrite` integration line by compiler PR
[#115](https://github.com/pcharbon70/catena/pull/115) at merge commit
[`646e117`](https://github.com/pcharbon70/catena/commit/646e11760396acb13fe9c182a320b53e1f899034).

## Evidence

The compiler adds the new `Catena.Text` module (`elaborate/2`
turning a scanned text, character, or bytes literal into its typed
`Text.Meaning`, total and deterministic, wrong-kind an
`ArgumentError`; `compare/2` over two same-kind meanings), extends
`Catena.Values` (binaries and elaborated meanings classify as
values, comparable, and orderable; binary comparison at the
`compare/2` level), extends `Catena.Data.comparable_type?/2` with
the `:Text`, `:Character`, and `:Bytes` type atoms, registers
revision `0.1.35`, and adds the `guides/language/data-model.md`
guide.

The focused corpus covers exact selection, lifecycle registration, and
pinned predecessor defaults; cooked text, hash-counted raw text,
character (code point 233), and escaped bytes elaborating to their
typed meanings with determinism; cooked/raw equal-content
equivalence; the wrong-kind `ArgumentError`; the classifier matrix
(binaries and elaborated meanings as values, comparable, orderable;
Unit still non-comparable; handles and closures still never; mixed
comparisons raising); the content orders at both the meaning and
binary levels; the type-atom admissions with `:List` and
`:Reference` rejected; and the collection/reference/frontend

## Version and boundary decision

C040 consumes `0.1.35` for the classification, the three types, the
elaboration operation, and the comparability entries; it adds no
JSON AST version, kernel S-expression version, interface version,
artifact version, signature domain, typing rule, runtime behavior,
BEAM representation, manifest field, or diagnostic family, and
amends no retained revision. Every predecessor API retains its exact
selection. The next unused semantic patch is `0.1.36`.
