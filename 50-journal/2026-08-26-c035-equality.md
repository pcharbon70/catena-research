# C035 Equality and Ordering

## Observations

Checklist item P035 is complete as C035 and normative source-only
language revision `0.1.30`, the first Section 4 *partial* to close.
The completed boundary fixes: the closed comparable set — Int, Bool,
and Float primitives plus structural recursion over tuples, records
(semantic, field order irrelevant), variant injections, and
constructor values — with ordering over Int and Float only; bit-exact
Float equality (`-0.0 != 0.0`) and total ordering (`-0.0 < 0.0`) with
no NaN under C018's finite-only contract; monomorphic comparison
(mixed Int/Float is the existing type error); closures and process
handles never comparable (`EQN001`, one new family); guards keeping
C003's frozen Int/Bool fragment; and built-ins now with an Eq/Ord
trait layer left to G101+/G061.

Five implementation decisions worth recording. First, the **witness
honesty adjustment**: planning-time inspection found the retained
JSON AST carries no float types and no float expression tags —
Floats exist only as elaborated C018 meanings and `Catena.Values`
values. Float comparison therefore cannot flow through
`check_json`/`compile_json` today; the float witnesses live at the
`Catena.Values` level (`comparable?/1`, `orderable?/1`, `compare/2`
with the signed-zero and denormal cases), while the evaluator and the
BEAM lowering ship correct-but-dormant total-order forms ready for
the first float-bearing frontend. Second, the **signed-zero
semantics were verified at runtime before writing code**: Elixir
`===` is bit-exact on OTP 27+ (`-0.0 === 0.0` → `false`) but `<`
ties the zeros — so both targets needed the total-order correction
(`a < b or (a === -0.0 and b === 0.0)` in the evaluator; `orelse`/
`andalso` compositions over `=:=`/`<` with float literals in abstract
format), rather than trusting `=:=` to cover ordering. Third, the
**guard split is enforced twice**: inference's general binary rule
widened to the comparable set while `Condition.core_type` still
admits only Int/Bool, so a Float or tuple comparison type-checks as a
general expression and rejects in a guard through the condition
checker — witnessed with tuple equality (general OK, guard `CND`).
Fourth, the **comparable-type check lives in `Catena.Data`** so
inference and the independent verifier share one definition
(`comparable_type?/2`, with nominal resolution through
`types_by_id`, constructor-field substitution, and conservative
rejection of abstract types without visible constructors and of
types containing variables). Fifth, the verifier's operand check
widened alongside inference's — ordering admits `:integer | :float`
only (Bool excluded), equality admits the comparable set — keeping
the two checkers aligned; the earlier `CND003` general-path
restriction is retired in favor of `EQN001`.

merged into the `rewrite` integration line by compiler PR

## Evidence

The compiler adds: `Catena.Values` `comparable?/1` (recursive over
both carriers, closures/handles/Unit excluded),
`orderable?/1`, and `compare/2` (the normative total order, bit-exact
floats, `ArgumentError` on mixed kinds); `Catena.Data.comparable_type?/2`
(shared by inference and the verifier); widened inference (ordering
over Int|Float, equality over the comparable set with `EQN001`);
widened verifier; total-order float forms in the evaluator and both
BEAM binary-lowering paths; the `0.1.30` registration; and the

## Version and boundary decision

C035 consumes `0.1.30` for the comparable set, float comparison
semantics, the classifier functions, the widened operator typing, and
`EQN001`; it adds no JSON AST version, kernel S-expression version,
interface version, artifact version, signature domain, manifest
field, or public API beyond the three classifier functions and the
shared type predicate, and amends no retained revision — C003's
fragment and C019's inventory stay frozen. Every predecessor API
retains its exact selection. The next unused semantic patch is
`0.1.31`.
