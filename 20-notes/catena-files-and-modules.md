# Catena Files and Modules

## Executive conclusion

A Catena source file should contain at most one module, named by a module
declaration whose concrete syntax belongs to P109, and the file's basename
minus its `.cat` extension must equal that declared name — a mismatch is
static invalidity, not a warning. Empty and comment-only files are valid
no-module files that builds ignore. File-level module names are ASCII
uppercase-initial words, identical to the retained JSON frontend's module
field. Generated files carry one exact first-line marker comment
(`// catena:generated by <tool>` on a C016 comment form) whose text is
inert anywhere else.

The executable deliverable follows the C015/C016 pattern: an abstract
file-unit resolver that consumes source bytes, a filename, and
parser-supplied module-declaration events, and validates multiplicity,
spelling, basename match, extension, and marker rules — fully testable
before P109's concrete header exists.

This closes G020 without deciding P109 declaration grammar, G021/G022 name
resolution, G025 package layout, G027 entry points, or G121/G128 build and
reproducibility policy.

## Scope and method

The operational target is independent agreement on the file-to-module
binding, the no-module case, the extension, name spelling, and generated
recognition. Primary comparative evidence comes from the official
[Erlang modules and code-loading documentation](../30-sources/erlang-otp-modules-and-code-loading.md),
the [Rust crates-and-modules reference](../30-sources/rust-project-2026-crates-and-modules.md),
and the [Haskell module findings](../30-sources/marlow-2010-haskell-language-report.md).
Source claims stay distinct from Catena proposals below.

## Relation to the current corpus

Both semantic frontends already fix the one-module unit: the retained JSON
AST carries exactly one `"module"` field matching `^[A-Z][A-Za-z0-9_]*$`,
and the [C010 kernel](../60-specification/formal-semantic-kernel/canonical-kernel-syntax.md)
is one `(module ModuleName ...)` form with imports bound to interface
digests. The file rule aligns with those decisions rather than adding a
second notion.

[C013 source text](../60-specification/source-text/README.md) supplies the
byte-accurate unit stream and spans the file layer consumes; [C016
comments](../60-specification/comments-and-documentation-comments/README.md)
supply the comment forms the generated marker rides on, including the rule
that `//`-comments are plain and `///`-comments are documentation. The
marker must therefore match a plain comment, and a `///` documentation
comment must never count as one.

[C019](../60-specification/operators-and-punctuation/README.md) supplies
the whole-source token stream that P109's declaration grammar will parse;
this slice deliberately stops above that grammar. The
[conformance vocabulary](../CONFORMANCE-VOCABULARY.md) requires every
mismatch outcome to be deterministic invalidity rather than loader
folklore.

## Comparative evidence and inference

### Erlang: declared name, verified by match

Erlang makes `-module(Name).` the mandatory first attribute and states the
name is to be the file name minus extension so code loading works; object
files are named after the module. The inference for Catena is that
declared-name-plus-basename-match keeps name-based artifact and tooling
lookup possible while keeping identity in file content. Catena upgrades the
rule from loader expectation to static invalidity with a stable diagnostic,
because C009 forbids leaving the failure mode to implementations, and
declines Erlang's atom-permissive naming for the ASCII word.

### Rust: derivation as the contrast

Rust files carry no header; module identity is the file's path relative to
the declaring module, held by the build. The inference is what Catena
avoids: without a header, "what module is this file?" is unanswerable from
content, and every tool must reproduce the path algebra. Rust demonstrates
the model scales, so Catena's header-plus-verification is a deliberate
determinism trade, not a claim the derived model is unworkable.

### Haskell: headers pair with file conventions

Haskell declares module names in headers, pairs them with `M.hs` by
tooling convention, and defaults missing headers to `Main`. Catena keeps
the declared-header shape, makes the file pairing a language rule, and
replaces the `Main` default with an explicit valid no-module file — module
identity should never be silently defaulted.

## Selected model

### File units

A Catena source file carries the `.cat` extension; the file-unit resolver
requires it. A file contains at most one module declaration; two or more
are static invalidity. A file with no module declaration is a valid
no-module file — empty files, whitespace-only files, and comment-only
files — which builds ignore. A no-module file never matches a basename and
never carries generated semantics beyond its marker.

### Names and matching

The module name comes solely from the declaration. File-level module names
are ASCII uppercase-initial words (`^[A-Z][A-Za-z0-9_]*$`), matching the
JSON frontend exactly and keeping basenames portable. When a module is
declared, the file basename minus extension must equal the module name;
mismatch is static invalidity identifying both the declared and expected
names.

### Generated markers

A generated file begins with one exact plain-comment marker:

```text
// catena:generated by <tool>
```

where `<tool>` is a nonempty ASCII identifier (`[A-Za-z0-9_-]+`). The marker
must be the file's first significant unit — only layout whitespace before
it — and at most one marker exists per file. The same text appearing after
any other significant unit, inside a documentation comment, inside a
literal, or inside a later comment's body is inert content. The marker
carries provenance for G128; editing and formatting policy stay with
G118/G123.

### Abstract resolver

A conforming implementation exposes a file-unit resolver accepting source
bytes, a filename, and parser-supplied module-declaration events (name and
span each), and returns the file unit — kind module or no-module, the
declared name when present, generated flag, and tool identifier when
generated — or exactly one diagnostic. It does not parse declarations,
resolve names, load code, or compile; the concrete header that produces the
events is P109's.

### Diagnostics

Five stable identifiers: bad extension, multiple module declarations,
invalid module-name spelling, basename mismatch, and malformed, misplaced,
or duplicate marker. Exact-selection mismatch remains `EDN001`.

## Rejected alternatives

- **Filename-derived module names (Rust):** identity becomes build-held
  positional state; files stop being self-describing.
- **Warning on mismatch (Erlang loader guidance):** leaves a deterministic
  failure mode implementation-dependent, contrary to C009.
- **Implicit default module (Haskell `Main`):** silently invents identity
  for headerless files; explicit no-module files say what they are.
- **Multiple modules per file:** contradicts both semantic frontends'
  one-module units and complicates artifact naming for no demonstrated
  need.
- **Filename-convention generated files:** conventions drift, collide with
  the basename rule, and carry no tool provenance.
- **Sidecar manifest for generated files:** a second file format this slice
  would have to specify; G025/G128 already own manifests.

## What C020 adds to the design

With the lexical layer closed, files gain identity: a build can map each
`.cat` file to its module by name, skip no-module files, and recognize
generated inputs with provenance. P109 receives a fixed file frame for its
declaration grammar, G025 receives file-level facts for package assembly,
and G118/G123 receive stable extension and marker contracts instead of
conventions.

## Remaining questions and falsification criteria

P109 must fix the concrete module-header syntax that emits declaration
events; G021/G022 must give module names their namespace meaning; G025 must
assemble files into packages and resolve duplicate module names across
files; G027 must select entry modules; G121/G128 must consume generated
provenance in builds.

The model should be revisited if P109's grammar needs a header form
incompatible with first-position declaration events, if G025 demonstrates
that one-module-per-file materially harms package assembly, or if the `.cat`
extension proves intolerable in practice (it collides with Windows security
catalogs; that cost was accepted explicitly).
