# Algebraic Data Types

## Executive conclusion

Algebraic data types give a program a closed vocabulary for constructing data
and a correspondingly checkable vocabulary for consuming it. Their value does
not come from compact enum syntax alone. One declaration simultaneously
establishes:

- a fresh nominal type constructor;
- a finite family of typed value constructors;
- recursive scope for inductive data;
- pattern forms for case analysis;
- the basis of exhaustiveness and redundancy checking;
- recursion and induction principles for suitable datatype shapes;
- lawful structural operations that may be derived; and
- semantic information from which a compiler may choose a representation.

For a greenfield Catena, the initial design should provide **closed, nominal,
ordinary parametric ADTs** in the principal Hindley–Milner fragment. Every
ordinary constructor must return the same declared result type, instantiated
only by the declaration's parameters. Matches should be ordered, pure at the
pattern boundary, and exhaustive by default. The compiler should reject
missing and useless cases and show concrete witnesses where it can.

The initial abstraction rule should also be sharp: a module either exports a
datatype's constructor interface or exposes the type abstractly. Code can
match only the constructors visible through its interface. Smart constructors
and ordinary observer functions should protect invariants; programmable views
or pattern synonyms can be investigated later, after their totality, effects,
coverage meaning, and evaluation cost are specified.

The surface datatype equation must not freeze memory layout. Tags, boxes,
payload packing, unboxed single-constructor types, and niche representations
belong to compilation. A stable C or binary layout should require a separate,
explicit representation contract.

Several nearby features should remain visibly separate:

- an **abstract datatype** hides a representation behind operations, whereas
  an **algebraic datatype** defines values with constructors;
- a **structural row variant** is extensible through a row variable, whereas a
  nominal ADT has one closed constructor family;
- a **GADT** permits constructors with refined result types and introduces
  branch-local type equalities, so it needs annotation-directed checking; and
- a **codata** or cyclic-object facility needs coinductive or graph semantics,
  not the finite structural-induction story of ordinary recursive values.

The initial proposal is therefore:

> Make ordinary ADTs boring, closed, nominal, inference-friendly, exhaustive,
> abstraction-aware, and representation-opaque. Derive only operations whose
> laws and traversal order follow from the declaration. Stage refinements,
> programmable matching, and stable layout as distinct features.

This is a fresh synthesis for the language imagined in this archive. It does
not rely on a Catena specification, implementation, or summary from another
repository.

## Scope and evidence standard

This note asks what a datatype declaration means in a strict, typed functional
language and what obligations follow for inference, matching, modules,
derivation, evolution, and compilation.

The main evidence route combines:

- [Burstall 1969](../30-sources/burstall-1969-structural-induction.md) for the
  proof principle generated by finite constructor-built data;
- [HOPE](../30-sources/burstall-et-al-1980-hope.md) for the early integration
  of declared constructors, parametric types, clausal matching, higher-order
  recursion patterns, and constructor hiding;
- [the revised Standard ML Definition](../30-sources/milner-et-al-1997-definition-standard-ml.md)
  for precise nominal generation, constructor typing, pattern status, ordered
  matching, and module abstraction;
- [Maranget 2007](../30-sources/maranget-2007-warnings-pattern-matching.md)
  for semantic coverage and usefulness analysis over typed pattern matrices;
- [Wadler 1987](../30-sources/wadler-1987-views-pattern-matching.md) for the
  tension between representation hiding and constructor-shaped patterns;
- [Leroy 1992](../30-sources/leroy-1992-unboxed-objects.md) for typed,
  representation-changing compilation across polymorphic boundaries; and
- [Peyton Jones et al. 2006](../30-sources/peyton-jones-et-al-2006-gadt-inference.md)
  for the inference boundary between uniform ordinary constructors and
  locally refining GADT constructors.

These works establish semantic structure and viable implementation methods.
They do not decide Catena's syntax or show that every proposed restriction is
usable. Corpus studies, an executable elaborator, diagnostic tests, and layout
benchmarks remain necessary.

## What “algebraic” means

### Sums, products, and units

The non-recursive fragment can be read as arithmetic over types:

| Type operation | Algebraic notation | Programming reading |
| --- | --- | --- |
| Empty type | `0` | no constructors and no values |
| Unit type | `1` | one nullary constructor |
| Product | `A × B` | a value contains an `A` and a `B` |
| Sum | `A + B` | a value is either an `A` or a `B` |
| Parameter | `A` | a position supplied by the type's caller |

Examples expose the arithmetic directly:

```text
Bool       = 1 + 1
Option A   = 1 + A
Result E A = E + A
Pair A B   = A × B
```

Constructor names carry evidence about which summand was selected. Fields
carry the product payload of that selection:

```text
type Result E A =
  | Err E
  | Ok A
```

This gives `Err` and `Ok` distinct runtime and pattern identities even when
`E` and `A` happen to be the same type.

The arithmetic analogy is exact for finite cardinalities: if `A` has `a`
values and `B` has `b`, then `A + B` has `a + b` and `A × B` has `a × b`.
With recursion, functions, divergence, abstract types, or infinite domains,
the analogy remains structurally useful but is not a complete semantic model.

### Recursion as a fixed point

A recursive datatype names the least finite structure closed under its
constructors. Informally:

```text
type List A =
  | Nil
  | Cons(A, List A)

List A = μX. (1 + A × X)
```

Likewise:

```text
type Tree A =
  | Leaf
  | Node(Tree A, A, Tree A)

Tree A = μX. (1 + X × A × X)
```

For a positive regular shape `F`, this fixed-point view explains why an
`F`-algebra `F R -> R` determines a fold `μF -> R`. The recursion-scheme
development in
[Meijer, Fokkinga, and Paterson 1991](../30-sources/meijer-et-al-1991-functional-programming-bananas.md)
makes those operators and fusion laws explicit.

Catena should not oversell the notation. A strict language with general
recursion also admits divergence, and not every recursively declared type is a
positive regular functor. Nested recursion, negative occurrences, function
fields, abstract components, and cyclic runtime graphs require more care.

### Algebraic does not mean abstract

The two phrases answer different questions:

- An **algebraic datatype** says how values are freely constructed and
  deconstructed.
- An **abstract datatype** says which operations clients may observe while
  hiding representation.

A module can implement an abstract set with an algebraic tree internally. It
can also publicly export an algebraic syntax tree whose constructors are the
intended interface. HOPE's tree example already shows the distinction:
constructor-based implementation and constructor hiding coexist rather than
compete.

## Declaration semantics

### A proposed surface form

The concrete spelling is illustrative, but it makes the semantic choices
testable:

```text
type Option A =
  | None
  | Some A

type Tree A =
  | Leaf
  | Node { left: Tree A, value: A, right: Tree A }
```

Elaboration should treat every alternative as one constructor with either no
payload or one product-like payload. Named fields are labels within that
constructor, not row-polymorphic records unless explicitly converted to one.
This keeps constructor application and constructor patterns aligned.

### Fresh nominal identity

Each declaration creates a fresh type identity:

```text
type UserId = UserId Int
type OrderId = OrderId Int
```

`UserId` and `OrderId` are not interchangeable merely because their shapes
match. Nominality prevents accidental mixing, gives modules a stable identity
to abstract, and lets the compiler change representation without structural
subtyping consequences.

A transparent alias must be a different declaration form:

```text
alias Meters = Float
```

An alias preserves identity; an ADT declaration generates it. If Catena later
supports explicit datatype replication, that operation should be visibly
non-generative rather than inferred from spelling or shape.

### Parameters, kinds, and constructor schemes

Type parameters are explicit declaration binders. For:

```text
type Option A = None | Some A
```

the generated constructor schemes are:

```text
None : forall A. Option A
Some : forall A. A -> Option A
```

For ordinary ADTs, every constructor's result is the declared type applied to
the same parameters. A constructor may omit a parameter from its payload, but
it may not refine the result:

```text
type Phantom A = Token              -- ordinary: Token : forall A. Phantom A

-- not an ordinary ADT constructor:
IntCase : TypedExpr Int
```

The second form is GADT territory because matching `IntCase` proves a local
equality between the index and `Int`.

Constructors are non-expansive values and their declaration-level type
variables are generalized. Constructor payload types are kind-checked in the
recursive environment; no value-level inference should invent missing
datatype parameters.

### Recursive and mutually recursive scope

All type names in a mutually recursive group must be in scope throughout the
group:

```text
type Expr =
  | Value Int
  | Let(Decl, Expr)

and Decl =
  | Binding(Name, Expr)
```

The declaration checker should:

1. allocate fresh nominal identities and check parameter binders;
2. add all group headers to the kind environment;
3. elaborate every constructor payload in that environment;
4. reject unsaturated or ill-kinded type constructors;
5. assign constructor schemes only after the group succeeds; and
6. publish the group atomically so a failed declaration leaks no identities.

The initial language may accept nested or negative recursive occurrences as
ordinary opaque payloads without granting them an initial-algebra interface.
Automatic `map`, fold, traverse, structural induction, and unboxed recursion
should be limited to shapes whose positivity and regularity checks justify
those operations. A stricter initial implementation may temporarily reject
other recursion, but that would be a usability restriction, not a requirement
of ordinary HM type safety.

### Constructor identity and namespaces

Patterns must distinguish a constructor from a variable before coverage
analysis. Relying on capitalization alone is fragile for tooling and qualified
imports. Catena should give constructors explicit resolved identities and let
source syntax use module qualification when ambiguity exists:

```text
Json.Null
Option.None
```

Whether unqualified constructor names share a namespace across types is a
surface-design choice. The semantic requirement is stronger: after name
resolution, a constructor pattern carries the constructor's nominal identity,
type scheme, arity, and parent datatype identity.

## Pattern matching is the elimination interface

### Core meaning

A constructor introduces a value; a match eliminates it:

```text
match value with
| None   -> fallback
| Some x -> use(x)
```

Catena should evaluate the scrutinee once, try rows from top to bottom, bind
the selected constructor fields, then evaluate that row's body. Constructor
tests themselves are pure observations of an already evaluated value. This
keeps coverage reasoning separate from arbitrary user code and leaves the
compiler free to generate a switch, decision tree, jump table, or another
equivalent strategy.

Top-to-bottom order remains observable when rows overlap through wildcards,
or-patterns, literals, nested patterns, or guards. Reordering is valid only
when the compiler proves it preserves matching and guard evaluation.

### Initial pattern vocabulary

The initial vocabulary should include:

- wildcard and variable patterns;
- nullary and payload constructor patterns;
- tuple and fixed-field constructor-payload patterns;
- literal patterns for types with specified literal equality;
- nested patterns;
- `as` patterns that name the whole matched value; and
- or-patterns whose alternatives bind exactly the same names at exactly the
  same types.

Repeated variable names in one pattern should be rejected instead of silently
becoming equality tests. Equality constraints belong in guards and require an
explicit `Setoid` dictionary.

Arbitrary function calls, effectful extractors, and view patterns should not
be initial pattern forms. They obscure evaluation count and order, turn
coverage into theorem proving, and can violate the premise that a constructor
pattern merely recognizes and decomposes a value.

### Guards

A guard runs only after its structural pattern matches:

```text
match n with
| Some x if x > 0 -> positive(x)
| Some _          -> non_positive
| None            -> absent
```

An arbitrary Boolean guard should contribute nothing to static exhaustiveness
unless it is a compiler-recognized constant `true`. This is conservative but
sound: proving a predicate total over an infinite domain is not the coverage
checker's job. Redundancy diagnostics should distinguish a structurally
unreachable row from a guard that merely appears contradictory.

### Exhaustiveness and usefulness

Coverage is a semantic property of the typed pattern matrix:

- a match is **exhaustive** when every possible scrutinee value reaches a row;
- a row is **useful** when it matches at least one value not accepted by all
  preceding rows; and
- a row is **redundant** when it is not useful.

Maranget shows that the same usefulness predicate supports both checks. To
test exhaustiveness, ask whether a final wildcard would be useful. To test one
row, ask whether it adds any value after the prefix before it. Recursive
specialization by the parent type's constructors yields concrete missing-case
witnesses.

Catena's initial policy should be:

- non-exhaustive `match` is a compile error;
- a useless row is a compile error, with a narrowly scoped lint downgrade only
  for generated code;
- diagnostics show at least one missing or shadowed pattern witness;
- refutable patterns in `let`, parameters, and comprehensions are rejected or
  must use an explicitly total result such as `Option` or `Result`; and
- a wildcard suppresses a future missing-constructor diagnostic only because
  the programmer deliberately accepted all remaining values, not because it
  is automatically inserted.

There should be no ordinary expression whose hidden behavior is “raise Match
at runtime.” Unsafe or foreign boundaries can expose a separately named
primitive if implementation work truly needs one.

### Difficult coverage cases

The checker needs explicit policies for cases that violate the simple closed,
inhabited-constructor model:

| Case | Initial policy |
| --- | --- |
| Empty type | an empty match is exhaustive when the scrutinee is statically uninhabited |
| Recursive empty type | use a bounded, terminating inhabitation analysis; remain conservative if unknown |
| Abstract datatype | clients cannot enumerate hidden constructors; consume through exported operations |
| Selectively visible constructors | require a wildcard for values outside the visible constructor set |
| Structural open variant | require a tail/wildcard case; analyze under its row semantics |
| Guarded row | do not count an arbitrary guard as covering its structural pattern |
| Or-pattern | expand semantically while preserving identical bindings |
| GADT | use branch equalities and inhabitation evidence in a later specialized checker |

Coverage must terminate even when nested patterns cause exponential worst
cases. The compiler should cap diagnostic witness expansion and record a
performance test corpus for adversarial matrices.

## Recursion, induction, and generic elimination

### Constructor-driven recursion

For finite constructor-built data, each recursive field is a proper
constituent. A structurally recursive function handles every constructor and
recurs only on those fields:

```text
length : List A -> Int
length xs = match xs with
| Nil        -> 0
| Cons(_, t) -> 1 + length(t)
```

Burstall's structural-induction rule mirrors exactly those cases. To prove
`P(xs)` for every finite list, prove it for `Nil` and prove it for `Cons(h,t)`
assuming `P(t)`. This is more than convenient syntax: the declaration supplies
the shape of definitions and proofs.

It does not prove termination automatically. A branch can recurse on the
original value, invoke general recursion elsewhere, or diverge while computing
a field. Mutable cycles and lazy infinite values also invalidate the simple
finite-constituent argument.

### Folds and direct matches

For a positive regular datatype, the compiler can derive a one-layer shape
functor and a catamorphism. For lists:

```text
fold_list : R -> (A -> R -> R) -> List A -> R
```

Direct matching should remain the ordinary language construct. A generated
fold is useful when it:

- centralizes traversal order;
- enables composition or fusion laws;
- feeds the `Foldable` vocabulary;
- provides a stable eliminator for an abstract interface; or
- avoids repeated hand-written recursion.

General recursion-scheme syntax should remain a library or research feature
until examples show that it improves code and diagnostics over matches plus
derived folds.

### Regularity and nested datatypes

`List A` recurs at the same parameter `A`; this is regular. A nested datatype
may recurse at a changed parameter:

```text
type Nest A =
  | One A
  | More (Nest (A, A))
```

Such a declaration can still have a clear operational meaning, but consumers
often require polymorphic recursion, which ordinary HM does not infer. Catena
should either stage nested datatypes or require explicit recursive signatures
for their consumers. It should not quietly weaken the principal-inference
claim for all ordinary ADTs.

## Ordinary ADTs and Hindley–Milner inference

Ordinary ADTs fit HM because constructor use is ordinary polymorphic function
use and constructor matching instantiates the same uniform result type.

For:

```text
Some : forall A. A -> Option A
```

constructing `Some 3` instantiates `A` with `Int`. Matching `Some x` against
`Option T` gives `x : T`; it does not learn that `T` equals a special type
selected by this constructor.

The required inference rules are therefore modest:

1. resolve and instantiate the constructor scheme;
2. unify its result with the expected scrutinee or expression type;
3. check the payload expression or pattern against the instantiated payload;
4. type every match body at one result type; and
5. run coverage on the elaborated typed patterns.

Nominal identities participate in unification as rigid type constructors.
Two same-shaped declarations never unify without an explicit conversion.

[Damas and Milner](../30-sources/damas-and-milner-1982-principal-type-schemes.md)
support principal inference for the rank-1 core; the Standard ML definition
shows how ordinary datatype schemes live inside such a language. The limits
still matter:

- polymorphic recursion needs annotations;
- higher-rank constructor fields need explicit checking boundaries;
- existential packages need an escape check;
- GADT results create local equalities; and
- strict effects constrain value generalization independently of ADTs.

### Why GADTs are a separate feature

Compare:

```text
-- ordinary
Some : A -> Option A

-- refined
IntLit  : Int -> Expr Int
IsZero  : Expr Int -> Expr Bool
```

In a match on `Expr A`, the `IntLit` branch learns `A ~ Int`, while the
`IsZero` branch learns `A ~ Bool`. Those equalities are scoped assumptions and
may make different branch-local programs typecheck. They also create
annotation and principality problems that ordinary constructor typing does
not have.

Catena should reserve refined result syntax for an explicitly enabled GADT
declaration. Its checker should require an enclosing signature, treat declared
indices as rigid, solve branch constraints locally, prevent equality evidence
from escaping, and avoid generalization under local equalities. The broader
constraint architecture belongs with
[OutsideIn(X)](../30-sources/vytiniotis-et-al-2011-outsidein.md), not in the
ordinary ADT elaborator.

## Abstraction and invariants

### Constructor visibility is authority

Exporting a constructor grants at least two capabilities:

- constructing values with its payload; and
- recognizing and decomposing values through its pattern.

Either capability may compromise an invariant or freeze representation.
Suppose a non-empty list is represented internally by ordinary list
constructors. If clients can construct `Nil`, the invariant is false. If they
can pattern-match the representation, replacing the implementation with a
tree becomes a breaking change even if every abstract operation is preserved.

The initial module interface should support two robust modes:

```text
-- transparent datatype interface: nominal type and listed constructors
export type Option A = None | Some A

-- abstract interface: nominal type identity and operations only
export type NonEmpty A
export make : A -> List A -> NonEmpty A
export head : NonEmpty A -> A
```

The defining module can always match its private constructors. Clients of the
abstract interface cannot. If selective exposure is admitted, the signature
must distinguish construction and matching authority; coverage then treats
unseen constructors as an unknown remainder.

### Smart constructors

A smart constructor validates before producing an abstract value:

```text
Email.parse : String -> Result EmailError Email
```

The result type makes failure explicit, preserves ordinary matching, and keeps
the representation hidden. This should be the first tool for invariants.
Calling a wrapper `type Email = Email String` does not itself ensure validity
if `Email` remains publicly constructible.

### Views and pattern synonyms

Views can translate a hidden representation into a public constructor-shaped
interface. They may improve readability and offer several decompositions of
one value, but they change the meaning of matching. Before Catena adds them it
must answer:

- Is the conversion total, pure, and terminating?
- Is it evaluated once per match or once per candidate row?
- Can it allocate or be asymptotically expensive?
- Are view alternatives disjoint and complete, and who verifies that claim?
- Does a view reveal enough information to invalidate representation
  independence?
- How do nested views affect coverage and usefulness?

A typed ordinary function returning an ADT is always available. Special
pattern syntax is justified only if it preserves clearer semantics or enables
better diagnostics than an explicit preliminary conversion.

## Representation and compilation

### Semantic shape is not physical layout

A conventional implementation may use a tag plus a payload:

```text
Option A  ~=  tag(None) | tag(Some) + payload(A)
```

But the following may all preserve the same source semantics:

- immediate integers for small nullary constructors;
- a pointer tag or spare-bit niche for `None`;
- packed tags and payloads;
- field reordering internal to an opaque declaration;
- unboxed payloads in monomorphic code;
- an erased wrapper for a single-constructor single-field type;
- shared constant objects for nullary constructors; and
- a uniform boxed representation at polymorphic or abstract boundaries.

Recursive values need indirection somewhere when an inline expansion would be
infinite, but the source declaration need not identify where. Mutually
recursive types may share layout strategies.

Leroy's translation shows why typed coercions between specialized and uniform
representations can be semantics-preserving and separately compiled. It also
shows why unboxing can lose: extra conversions may cost more than the removed
allocation.

### Representation contracts

Catena should define three levels:

1. **Default:** layout is entirely opaque and may vary by compiler version,
   target, optimization level, and use site.
2. **Stable language ABI:** an explicit attribute fixes tag order, field order,
   size/alignment rules, and compatibility obligations for separately compiled
   Catena components.
3. **Foreign or wire representation:** an explicit schema defines invalid bit
   patterns, endianness, padding, versioning, and validation at the boundary.

Constructor declaration order may define source-level derived ordering without
also defining numeric runtime tags. Debuggers and reflection should consume
compiler metadata rather than infer layout from source order.

### Runtime checks and impossible states

Well-typed internal code should not construct an unknown tag. Foreign memory,
deserialization, unsafe casts, or version-skewed data can. Crossing those
boundaries must validate the representation before producing a trusted ADT.
An “impossible” default branch in generated code is a backend integrity guard,
not part of ordinary match semantics.

## Derivation

### Derive from structure, not from a familiar name

A declaration contains enough information to synthesize some operations, but
not every algebraic interface has a canonical instance.

| Derived capability | Structural condition | Required semantic choice |
| --- | --- | --- |
| `Setoid` | every compared field has `Setoid` | constructors unequal; fields compared in declaration order |
| `Ord` | every ordered field has `Ord` | explicit constructor precedence and lexicographic field order |
| `Functor` | selected parameter occurs only covariantly | preserve constructors and all non-parameter fields |
| `Bifunctor` | two selected parameters occur covariantly | declare which two kind positions are mapped |
| `Foldable` | selected parameter occurs in traversable fields | specify left-to-right constructor-field order |
| `Traversable` | lawful `Functor` and `Foldable` shape | preserve that same applicative effect order |
| recursive `fold` | positive regular recursive shape | one algebra method per constructor |
| debugging display | every displayed field is printable | label and redaction policy |
| stable encoding | explicit schema, not shape alone | tags, versions, unknown fields, and compatibility |

`Semigroup`, `Monoid`, `Apply`, `Applicative`, `Chain`, `Monad`, `Extend`,
`Comonad`, `Category`, and `Arrow` generally do not follow canonically from an
arbitrary constructor tree. The compiler must not derive them merely because
the names appear in Catena's categorical hierarchy.

### Positivity, variance, and failed derivations

For:

```text
type Consumer A = Consumer (A -> Int)
```

`A` occurs contravariantly, so the declaration does not determine
`map : (A -> B) -> Consumer A -> Consumer B`. The compiler should reject a
requested `Functor` derivation and point to the negative occurrence.

Phantom parameters are different: a lawful map can ignore its function because
no `A` exists to transform. Mixed positive and negative occurrences reject a
covariant derivation even if a programmer can write some function with the
same method type.

For recursive folds and traversals, regularity matters as well as positivity.
The diagnostic should name the recursive occurrence whose changed parameters
require polymorphic recursion rather than reporting a generic “cannot derive.”

### Laws and operational order

Generated code gives stronger evidence than an arbitrary user-written
instance only when the derivation algorithm and assumptions are specified.
Catena should record the evidence as “compiler-derived,” expose the generated
constraints, and test the generator against the class laws.

Extensional laws still do not fix cost or effect order. A derived traversal
must state its constructor-field order because applicative effects observe it.
A derived ordering must state constructor precedence because adding or
reordering alternatives changes sorted collections and persistent data.

## Evolution and compatibility

Closed constructor sets enable strong coverage checking, but that benefit has
an evolution cost:

- adding a constructor breaks exhaustive downstream matches;
- removing or renaming one breaks construction and matching;
- changing a payload breaks both constructor application and patterns;
- changing constructor order may break derived `Ord` or stable encoding; and
- hiding previously public constructors breaks representation-dependent code.

Those are useful failures: the compiler locates every client whose assumption
about the closed world must be reconsidered.

For APIs expected to gain alternatives without rebuilding clients, Catena
should require a visibly different contract, such as:

- an abstract type with observation functions;
- a public `non_exhaustive` marker that requires an external wildcard;
- a versioned wire schema with an unknown-alternative case; or
- a structural open variant row when anonymous extensibility is the actual
  requirement.

It should not silently make every nominal ADT open. That would surrender both
closed-world reasoning and precise missing-case diagnostics.

## Nominal ADTs versus structural variants

Both represent alternatives, but they optimize for different identities:

| Property | Nominal ADT | Structural row variant |
| --- | --- | --- |
| Identity | declaration-generated type name | label/payload structure |
| Constructor family | closed by declaration | may have an open row tail |
| Extension | new declaration or breaking edit | row extension/composition |
| Match completeness | enumerate declared constructors | handle known labels plus tail |
| Abstraction | hide nominal type or constructors | quantify/constrain labels |
| Inference machinery | ordinary constructor schemes | row unification and lacks predicates |

[Gaster and Jones](../30-sources/gaster-jones-1996-extensible-records-variants.md)
give the structural design its own effective inference account. Catena should
support the two forms without subtyping one into the other. Explicit injection
and projection functions can cross the boundary when an API needs both stable
nominal identity and structural composition.

## Diagnostics are part of the feature

Useful ADT errors should preserve declaration and pattern provenance. Examples
include:

```text
non-exhaustive match on Result ParseError Config
missing case: Err(_)
declared at config.cat:18
```

```text
unreachable pattern: Some(_)
the earlier pattern `_` already covers this value
```

```text
cannot derive Functor for Parser A
parameter A occurs contravariantly in field `run : A -> Token`
```

```text
constructor `Node` belongs to Syntax.Tree, not Json.Value
while checking pattern against Json.Value
```

```text
cannot match abstract type Email
its constructors are hidden by module interface Accounts
consider Accounts.domain or Accounts.to_string
```

Coverage witnesses should be bounded in size, use source constructor names,
respect hidden interfaces, and avoid suggesting constructors inaccessible in
the current module.

## Design sketch for Catena

### Initial declaration contract

An initial implementation should commit to:

1. fresh nominal identity per datatype declaration;
2. explicit kinded parameters and atomic mutual declaration groups;
3. nullary or product-payload constructors with uniform result types;
4. ordinary constructor schemes in rank-1 HM inference;
5. pure constructor patterns with resolved nominal identities;
6. top-to-bottom match semantics and single scrutinee evaluation;
7. exhaustive and useful matching as compile-time requirements;
8. concrete bounded witnesses for coverage errors;
9. transparent or abstract constructor export through module signatures;
10. opaque default representation and validated unsafe boundaries; and
11. explicit, conditional derivation with documented laws and order.

### Staged extensions

Add only with separate semantics and evidence:

- selective construct-versus-match visibility;
- `non_exhaustive` public nominal types;
- view patterns or bidirectional pattern synonyms;
- nested and generalized recursive datatypes if the initial checker restricts
  them;
- GADTs with annotation-directed local equality solving;
- existential constructor payloads;
- first-class datatype reflection;
- stable native and foreign layout attributes;
- codata, cyclic immutable graphs, or guarded recursion; and
- proof-producing positivity, termination, or inhabitation analysis.

### Required compiler phases

```text
source declaration
  -> name and kind headers
  -> recursive payload elaboration
  -> constructor schemes and visibility
  -> typed patterns and branch bodies
  -> coverage/usefulness analysis
  -> derived instances and eliminators
  -> decision-tree match compilation
  -> representation selection
  -> typed lower-level IR verification
```

Coverage should run after type-directed constructor resolution but before
layout selection. Match compilation may share typed pattern data with coverage
without treating a backend decision tree as the definition of usefulness.

## Attractive claims that do not survive scrutiny

### “ADTs are just enums with payloads”

This misses recursive scope, polymorphic constructor schemes, abstraction,
induction, coverage, and derivation. Enum lowering is one implementation
strategy, not the language meaning.

### “Algebraic datatype” and “abstract datatype” are synonyms

One exposes a constructor algebra; the other hides representation. A public
syntax tree is algebraic but not abstract. A set interface may be abstract
while its internal representation is algebraic.

### “A wildcard makes a match future-proof”

It prevents a compile error when constructors are added, but may silently give
new semantically important cases the old default behavior. It is appropriate
only when that fallback is the intended policy.

### “Make invalid states unrepresentable” happens automatically

An ADT removes states only when its public constructors and fields actually
exclude them. Public `Email String` still admits every string. Abstract
construction, refined indices, validation, or proof-carrying fields may be
needed.

### “The datatype equation determines layout”

It determines values and eliminations at the source level. Boxing, tag values,
niches, alignment, and wrappers remain compiler choices until an ABI contract
fixes them.

### “GADTs are ordinary ADTs with nicer constructor annotations”

Refined results generate branch-local equality evidence and change the
inference problem. Treating them as a cosmetic extension makes principal-type
and escape failures appear arbitrary.

### “Structural recursion proves termination”

Only a checked restriction that every recursive call decreases along a
well-founded constituent relation would justify that claim. Ordinary pattern
matching can express both terminating and diverging functions.

## Tradeoffs and falsification tests

The proposal deliberately favors predictability. It should change if evidence
shows that the restrictions defeat ordinary programs.

| Hypothesis | Evidence that would weaken or falsify it |
| --- | --- |
| Exhaustive matches should be errors | a representative corpus needs pervasive deliberate partiality that explicit `Option`/`Result` makes materially less clear |
| Ordinary ADTs preserve principal inference | the reference inferencer finds ordinary uniform-result examples requiring non-principal choices |
| Transparent-or-abstract export is enough initially | common invariant-preserving APIs need read-only patterns that observers cannot express clearly or efficiently |
| Programmable views can wait | explicit conversion creates repeated asymptotic work or destroys important equational structure in real libraries |
| Default layout should be opaque | separately compiled Catena libraries cannot meet interoperability needs with explicit ABI opt-ins |
| Derivation should be structural and selective | a non-structural class has one canonical lawful instance across a broad datatype corpus |
| Nominal and row variants should stay distinct | conversions dominate real programs and a unified formalism retains identity, openness, inference, and diagnostics without ambiguity |
| GADTs should be staged | essential initial APIs cannot be expressed with ordinary ADTs, abstract modules, and explicit existential packages |

## Research and implementation agenda

1. Define a small declarative calculus for nominal ordinary ADTs, mutual
   recursion, patterns, matches, and constructor visibility.
2. Extend the executable HM inferencer with declaration elaboration and a
   typed pattern judgment; prove or test conservativity over the pure core.
3. Implement usefulness-based coverage with witnesses, empty-type awareness,
   guards, or-patterns, and hard complexity limits.
4. Specify the public module signature distinction between transparent and
   abstract datatype exposure.
5. Define positivity, regularity, variance, and derivation checks independently
   of basic datatype well-formedness.
6. Generate and verify `Setoid`, `Ord`, `Functor`, `Bifunctor`, `Foldable`,
   `Traversable`, and regular folds against the categorical hierarchy.
7. Build a pattern corpus containing empty, singleton, nested, mutually
   recursive, abstract, open-row, and adversarial cases.
8. Prototype tag, niche, boxing, and wrapper strategies behind one typed layout
   interface; measure allocation, code size, conversion cost, and debug
   quality.
9. Write explicit source and binary compatibility rules before exposing stable
   layout or `non_exhaustive` APIs.
10. Evaluate GADTs and views only in separate calculi with their annotation,
    effect, coverage, and abstraction costs visible.
